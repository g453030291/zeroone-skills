# 行业情报流水线

把一池原始资讯变成少量值得读的判断。链路：**采集 → 去重入库 → 关注点过滤 → 话题聚类 → 成稿判定 → 写情报 → dashboard**。

## 分工（先读这段）

上游一次返回约 100 篇、**34 万字**。全部读进上下文，一轮就烧掉十几万 token。所以：

- **脚本做机械活**：拉数据、去重、关键词打分、算相似度、查冷却期、统计。这些不需要你参与。
- **你做语义判断**：脚本给你紧凑 JSON（标题 + 短摘要），你在上面决定过滤、合并、命名，再用 `--apply` 写回。
- **只有写稿那一步读全文**，且只读被选中的那几篇。

发现自己在读大段正文而还没到写稿环节，就是走错了——退回去用脚本。

脚本在 `scripts/`，只依赖 Python 3 标准库。数据在 `~/.zeroone/`（`ZEROONE_HOME` 可改），刻意放在 skill 之外，因为这个仓库是开源的。下面的命令都在 `scripts/` 下执行。

## 第 0 步 · 初始化（只做一次）

```bash
python3 store.py --status
```

看 `has_key` 和 `profiles` 两个字段。

### 配置接口 key

`has_key` 为 false 时，**向用户索取接口 key**。这个 key 是数据方管控用户准入的唯一凭证，所以不内置、不共享、不写进仓库：

```bash
python3 store.py --set-key <用户给的 KEY>
```

存到 `~/.zeroone/config.json`（权限 600），同系列 skill 共用。之后每次请求的 header 都从这里读。用户没给就停下来问，不要猜、不要找替代来源。

### 建关注点

`profiles` 为空时，先问清三件事，别自己替用户决定：

1. 关注什么行业 / 公司 / 话题？
2. 关注它哪个侧面？（产品动态？人事？融资？技术路线？政策？）
3. 什么明确不想看？（招聘、课程推广、纯教程…）

然后**由你把它扩写成关键词集合**——这是你在这一步的价值。用户说"关注新能源汽车"，关键词里就该有具体车企（比亚迪、蔚来、理想、小鹏、极氪、问界）、技术词（增程、固态电池、800V、智能座舱）、上下游（动力电池、轮胎、充电桩）。粗筛完全靠这张表做第一层召回，**表越全漏得越少**，20-30 个词是合理起点。

关注点存在 `~/.zeroone/industry-insight/profiles.jsonl`，**一行一个，你直接编辑这个文件**（没有也没必要有管理脚本）：

```json
{"slug":"auto-industry","name":"汽车行业","description":"关注中国新能源整车厂的产品、销量、人事与技术路线","include":["比亚迪","蔚来","理想","小鹏","极氪","问界","增程","固态电池","800V","智能座舱","动力电池","充电桩","销量","车展"],"exclude":["招聘","课程报名","直播预告"]}
```

一行写完，别换行——JSONL 的可读性就在于一眼能扫完所有关注点。用户想加关注点或改关键词，直接加行/改行即可。

## 第 1 步 · 采集

```bash
python3 ingest.py --run
```

输出 `{returned, inserted, duplicates, total_articles}`。接口每次返回最新约 100 条，历史靠反复轮询累积，所以第一次跑 `inserted` 接近 100，之后大部分是 `duplicates`——这是去重在生效。装了定时任务（见下）就不用手动跑。

接口细节见 `references/data-source.md`。

## 第 2 步 · 关注点过滤

```bash
python3 relevance.py --profile <slug>
```

输出 `{id, feed, title, kw_score, matched}` 的紧凑表，按分降序。`kw_score` 只是关键词命中的机械打分，是排序线索，不是结论。

三类判断：

- **高分且标题对题** → 确认 `hit`
- **零分低分但标题看着相关** → 捞回来。这是你相对纯关键词方案的核心价值：一篇讲"某车企换帅"的文章可能一个品牌词都没提，但它显然属于行业动态。
- **拿不准** → `--snippets id1,id2` 调 200 字摘要再看。同一个 id 可能对应多个信源（复合主键是 `id + source_type`），拿不准指哪条时用 `id@source_type` 精确指定；返回结果里 `ambiguous: true` 就是在提醒你裸 id 撞了不止一条。

写回：

```bash
cat > /tmp/v.json <<'EOF'
[{"id":"...","source_type":"wx","score":0.9,"verdict":"hit","reason":"整车厂人事动态"},
 {"id":"...","source_type":"wx","score":0.1,"verdict":"miss","reason":"NLP 论文解读，与汽车无关"}]
EOF
python3 relevance.py --profile <slug> --apply /tmp/v.json
```

**每一篇都要判定，包括 miss 的**——已判过的下次不再出现，漏判会让它反复出现。宁可宽松：miss 掉的就彻底出局了，多收的会在聚类和成稿判定两道关口被自然过滤。

**`verdict` 只接受 `hit` / `miss`，写错会被拒绝**（`--apply` 的返回里看 `invalid_verdicts`）。别自己发明第三种状态——记录一旦写入但值不对，这篇文章既不算命中也不会再出现在待判表里，等于永久消失且没有报错。

## 第 3 步 · 话题聚类

```bash
python3 cluster.py --profile <slug>
```

默认**只看还没归入任何聚类的新文章**——不然跑得越久候选表越臃肿，每天都要重新过一遍几天前已经处理好的旧文章。改了阈值、想整体重新分组时用 `--full` 连旧文章一起重来。

脚本用中文字符 bigram 的 TF-IDF 做**预聚类**，返回 `groups`（候选组，带 200 字摘要）和 `singletons`。它只看字面重合，必然有两类错误等你修：

- **该合没合**：同一件事换个说法就配不上。"雷军谈增程路线"和"小米澎程定名"是一回事但共享字词很少。**扫一遍 singletons 把同一件事合起来**——这是你这步最主要的工作。
- **不该合合了**：只共享行业词的被凑成一对（"轮胎实力榜"和"补胎气囊事故"都在讲轮胎，不是一件事）。拆开。
- **`【XX快讯】` 这类一篇塞五条消息的合集**很容易和多个话题都沾边。以第一条消息定主题，或干脆不放进任何组。

```bash
cat > /tmp/t.json <<'EOF'
[{"topic_key":"shangqi-reshuffle","title":"上汽同日调整两大板块一把手","members":["id1","id2","id3"]}]
EOF
python3 cluster.py --profile <slug> --apply /tmp/t.json
```

`topic_key` 用小写英文短横线 slug，**跨天要稳定**——同一件事下次尽量复用同一个 key，这是冷却期识别同话题的第一条线索（第二条是文章 id 重合度，兜底）。

每次 `--apply` 传的 `members` 是这个 `topic_key` **当下应有的完整名单**，不是增量——脚本会按这份名单全量替换该聚类的成员。想把一个话题从 4 篇拆成 1 篇，或者纠正一次错误配对，直接在名单里去掉多余的 id 重新 apply 即可，旧成员不会遗留。

嫌松嫌紧调 `--threshold 0.12`（更松）/ `0.25`（更紧），默认 0.15 是实测平衡点。

## 第 4 步 · 成稿判定

```bash
python3 digest.py --plan --profile <slug>
```

| action | 含义 | 你该做什么 |
|---|---|---|
| `write` | ≥2 篇且来自 ≥2 个独立公众号，不在冷却期 | 在今天的情报里占一节 |
| `update` | 3 天内写过，但有新增文章 | 写一小节增量更新，说清新进展和判断有没有变 |
| `same_feed` | ≥2 篇但全来自同一个公众号 | 默认跳过——这不是真正的跨源印证 |
| `single` | 只有 1 篇 | 默认跳过 |
| `skip` | 3 天内写过且无新增 | 跳过 |

**为什么 ≥2 篇且要独立信源**：单篇重写一遍只是洗稿，同一个公众号发两篇也一样——那只是它自己更新了说法，不构成交叉印证。这条流水线的价值在于真正的多信源比对：几家媒体说法差在哪、谁给了别人没有的数据、谁立场明显不同。`same_feed` 就是脚本替你把"篇数够但其实是一个声音"这种情况单独挑出来，别把它和真正的跨源混在一起自动写。

**为什么 3 天冷却**：每天把同一结论换个说法再讲一遍，既烧 token 又训练用户跳过你的产出。

`single` 和 `same_feed` 都可破例，但要够格：重大事件（大额并购、监管落地、重要人事、安全事故）且信息量确实足。破例时在那一节的 `source_note` 里写明只有单一信源（或单一公众号），别让读者误以为得到了相互印证。

**全部为空是合法结果。** 冷清的日子写不出东西很正常，如实说明即可。这条流水线的价值之一就是它敢于不产出。

## 第 5 步 · 写当日情报

对每个 `write` / `update` 的聚类取全文——**整条流水线唯一读正文的地方**：

```bash
python3 digest.py --content <cluster_id>
```

产出是**结构化 JSON**，不是 markdown。用 Write 工具把它直接写到这个路径（今天、这个 profile 只有一份，文件不存在就新建）：

```
~/.zeroone/industry-insight/summaries/<profile>/YYYY-MM-DD.json
```

`--record` 默认按 `--profile` + `--date`（不传就是今天）推算这个路径，不需要额外传 `--file`。dashboard 直接渲染这个文件，不需要解析任何东西。完整 schema 和写作标准见 `references/output-format.md`（**写稿前必读**），骨架：

```json
{
  "highlights": ["今天值得看的第一件事，带上关键数字", "...", "..."],
  "topics": [{
    "topic_key": "...", "cluster_id": 3, "title": "...",
    "tldr": "两三句说清这件事和它的意义",
    "facts": [{"text": "事实陈述，数字照抄原文", "url": "原文链接"}],
    "cross_source": "几家说法差在哪、谁给了独家数据、谁立场不同",
    "source_note": "点破伪交叉信源，没有就省略",
    "implications": ["分析判断，说明依据"]
  }],
  "skipped": [{"topic_key": "...", "title": "...", "reason": "3 天内已写过"}]
}
```

你只写这四块。`sources`、`article_ids`、`stats`、`generated_at` 全部由脚本回填——别手写，手抄容易漏而冷却期依赖它们。`topics[].cluster_id` 必须是**当前这个 profile 自己的**聚类 id——脚本会校验，填了别的 profile 的 cluster_id 会直接拒绝登记，不会把别的行业的文章串进来。

写完登记（会校验必填字段、校验 cluster 归属、回填信源、算统计）：

```bash
python3 digest.py --record --profile <slug>
```

读者是**普通用户，不是行业分析师**：说人话、不堆黑话、事实和观点分开标。

**`source_note` 是容易忽略但很重要的一项。** 经常出现两种伪交叉：同一公众号一天发两篇讲同一件事，或关联账号转发同一份通稿。看着 2 个信源实际只有 1 个，碰到就点破，别让读者误以为得到了相互印证。

## 第 6 步 · dashboard

```bash
python3 dashboard.py --open
```

单文件、零外部依赖、双击即开、断网也能看。展示六节点漏斗、关注点切换、每日情报（含"今日采集/新增/扫描/命中/引用渠道"的用量条）、话题聚类、信源分布。跑完一轮**主动生成**并把路径给用户。

## 完整一轮

```bash
python3 relevance.py --profile <slug>        # → 判定 → --apply
python3 cluster.py   --profile <slug>        # → 合并命名 → --apply
python3 digest.py    --plan --profile <slug> # → 逐个 --content → 写 JSON → --record
python3 dashboard.py
```

跑完给用户一段简短汇报：新增多少篇、命中多少、聚出几个话题、收了哪几个、跳过了什么以及为什么。**跳过的理由和产出一样重要**——它证明流水线在做筛选。

## 自动化

**调度交给运行这个 skill 的环境，skill 自己不装任何系统定时任务。** 装在 Claude Code 就用 Claude Code 的定时任务，装在 workbuddy 就用 workbuddy 的。宿主自己管生命周期、日志和权限；越过它去改用户的 crontab 或 LaunchAgent，用户会在一个根本想不到的地方多出一个删不掉的后台任务。

用户要定时跑时，**排两个作业**——采集和分析的成本差着数量级，绑在一起会被贵的那个拖住频率：

**作业一 · 采集，一天 3 次**（约每 8 小时）。内容只有一行，不需要任何判断：

```bash
python3 ingest.py --run
```

**为什么必须一天多次**：上游是滚动窗口，实测 100 条只覆盖约 **12.5 小时**。一天只采一次，等于每 24 小时里只看得见 12.5 小时，**另一半永久丢失且不会有任何报错**——你看到的一切都正常，只是数据有洞。8 小时一次留 4 小时缓冲。

**作业二 · 分析产出，一天 1 次**，跑上面第 2-6 步。

动手前先确认数据是新的：

```bash
python3 store.py --status     # 看 hours_since_fetch
```

超过 12 小时说明采集那个作业没在跑或跑挂了，先补一次 `ingest.py --run`，并提醒用户去检查作业一。

### 无人值守时格外克制两点

- **不确定就跳过。** 没人在旁边纠正你。相关性和聚类合并宁可保守——收错一篇只是多段废话，错误合并会把两件事写成一件。
- **没内容就说没内容。** 自动运行最容易滑向"每天必须交作业"，把单篇消息硬凑成话题。`topics` 给空数组、在 `highlights` 里说明原因，是合格产出。

## 常见情况

**用户想同时看多个领域** → profiles.jsonl 加行。文章只存一份，相关性按 profile 分别打分，加关注点不需要重抓。dashboard 标签页可直接对比不同关注点的漏斗差异。

**key 失效 / 401 403** → 不要绕过，也不要找别的数据来源。告诉用户 key 可能被回收了，让他们找数据方确认。

**用户想回看某天** → `python3 digest.py --list --profile <slug>`。

**接口连不上** → `ingest.py --from-file <json>` 可回放本地保存的响应，用于离线演示。

**想快速演示不碰真实数据** → `ZEROONE_HOME=/tmp/demo python3 ...`，整个工作区建在临时目录。
